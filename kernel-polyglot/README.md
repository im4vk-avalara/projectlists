# kernel-polyglot

A 1018-byte file that is simultaneously:

1. A legacy-BIOS-bootable **MBR** — boots in QEMU and on real PCs.
   Displays a static centred banner with a rainbow background-colour wave
   sweeping behind it.
2. A valid **ZIP** archive — opens with `unzip`, `zipinfo`, `python -m zipfile`,
   contains a single `README.txt`.
3. A valid **PDF** document — parses with `pdfinfo`, `qpdf`, macOS PDFKit;
   reports "Pages: 1, PDF version: 1.4."

All three formats validate with **no errors and no warnings** from any
parser tested.

Educational project demonstrating x86 real-mode assembly, the BIOS boot
process, file-format structural design, and byte-level sizecoding.

---

## Quick start

```sh
make doctor          # verify host has Docker, QEMU, Python, etc.
make                 # build boot.img (1018 B polyglot)
make test            # run all three format validators (headless, ~15 s)
make run             # boot in QEMU and watch it live (opens a window)
```

`make help` lists every target with a one-line description.

## What you'll see in QEMU

`make run` opens a QEMU window. After the SeaBIOS banner you'll see:

```
                                                                       (row 12, col 25)
                            * kernel-polyglot - Stage 2 *
```

…with the **background** of every cell on every row cycling through 8
colours in a wave that sweeps left-to-right and top-to-bottom. The banner
text stays white-on-whatever-colour, so it's readable through every
phase. Frame rate is ~33 fps, paced by `INT 15h AH=86h`.

(The "Stage 2" in the banner is historical — Stages 3 and 4 added file
formats around this boot code without modifying it.)

## Why these choices

- **Assembler: NASM** — Intel syntax, dominant in OS-dev / sizecoding,
  runs inside a throwaway Alpine container (zero install on the macOS
  host). The Dockerfile is 2 lines (`tools/Dockerfile.nasm`).
- **Size: 1018 bytes**, not the classic 512. The user budget was raised
  to ~1 KB so we could fit ZIP + PDF without crippling the visual.
  BIOS still loads only the first 512 bytes into RAM and executes them;
  everything past byte `0x1FF` is cold data, visible only to file-format
  parsers.
- **Boot mode: legacy BIOS only.** Not UEFI. Targets
  `qemu-system-i386 -drive format=raw`.
- **Real mode only.** No protected mode, no paging, no stage-2 loader.
- **Boot signal: direct VGA writes**, not INT 10h teletype. The hot path
  is `stosb` into segment `0xB800`, ~10 B/cell per loop iter vs ~15 B/char
  via teletype, and it gives us 80×25 = 2000 cells in well under a frame.

## How it works

The three formats coexist because each anchors on a **different point** in
the file:

- **BIOS** anchors on byte `0x1FE`: reads sector 0 (the first 512 bytes),
  jumps to linear `0x7C00` only if bytes 510/511 are `55 AA`. It never
  looks past byte 511.
- **PDF** parsers anchor on the `%PDF-` header (must lie within the first
  1024 bytes of the file) and `%%EOF` (scanned backward from end-of-file).
- **ZIP** parsers anchor on the **End of Central Directory** record
  (`PK\5\6`) at the *end* of the file. The EOCD's `offset_to_central_dir`
  field is then followed to the central directory, which points to each
  Local File Header.

Visually:

```
0x000 ─ BIOS reads from here ──────────────────────────┐
┌──────┬────────────────────────┬────────────┬─────────┴┐
│ boot │      PDF body          │ zero pad   │  55 AA   │
│ code │  %PDF-1.4 ... %%EOF    │            │          │
└──────┴────────────────────────┴────────────┴──────────┘
        ▲
   %PDF- (PDF anchor)
                                                      0x200
                                          ┌─────┬──────────────┬──────┬──────┐
                                          │ LFH │  README data │ CDFH │ EOCD │
                                          └─────┴──────────────┴──────┴──────┘
                                                                          ▲
                                                              ZIP scans back from here
```

The shared bytes:

| Range | MBR | PDF | ZIP |
|---|---|---|---|
| `0x000..0x067` | **executed boot code** | prefix (ignored) | prefix (ignored) |
| `0x068..0x196` | loaded, **never executed** | **PDF body** (parsed) | prefix (ignored) |
| `0x197..0x1FD` | loaded, unused | trailing (ignored) | prefix (ignored) |
| `0x1FE..0x1FF` | **boot signature** | trailing | prefix |
| `0x200..0x3F9` | (BIOS doesn't load this far) | trailing | **ZIP archive** |

`0x068..0x196` is where genuine byte sharing happens: BIOS loads those
303 bytes into RAM at linear `0x7C68`, but our boot code's infinite
animation loop never reads past byte `0x048`, so the PDF content is inert
at boot. PDF parsers see exactly those 303 bytes as the entire PDF.

### The PDF-relative offsets gotcha

The empirical lesson from Stage 4: when a PDF sits behind a non-PDF
prefix, `startxref` and the xref-entry byte offsets should be counted
**from the `%PDF-` header**, not from byte 0 of the containing file.
Strictly ISO 32000-1 says "from the beginning of the file," but every
major parser tested treats `%PDF-` as the origin when a prefix is present.
File-relative offsets cause:

| Parser | File-relative offsets | PDF-relative offsets |
|---|---|---|
| `pdfinfo` (Poppler) | accepts cleanly | accepts cleanly |
| `qpdf --check` | *"file is damaged, attempting reconstruction"* | *"No syntax or stream encoding errors found"* |
| macOS PDFKit | 3 debug warnings, accepts after fallback | silent, accepts |

PDF-relative offsets make all three completely silent. See
`tools/build_polyglot.py:build_pdf` for the byte-by-byte construction
that emits them.

### Boot-code anatomy (the 104 bytes at offset 0)

Annotated by NASM listing (`boot.lst` is regenerated by every build):

```
Offset  Bytes        Asm                    Purpose
──────  ───────────  ────────────────────   ─────────────────────────────────
0x000   FA           cli                    IRQs off across SS/SP write
0x001   31 C0        xor ax, ax             AX = 0
0x003   8E D8        mov ds, ax             DS = 0 (lodsb reads banner @ 0x7C4A)
0x005   8E D0        mov ss, ax             SS = 0
0x007   BC 00 7C     mov sp, 0x7C00         stack grows down below our code
0x00A   FB           sti                    IRQs back on
0x00B   B8 00 B8     mov ax, 0xB800         VGA text-buffer segment
0x00E   8E C0        mov es, ax             ES = 0xB800
                                            ── clear screen ─────────────────
0x010   B8 20 0F     mov ax, 0x0F20         AH=0x0F attr (white/black), AL=' '
0x013   B9 D0 07     mov cx, 2000           80*25 cells
0x016   31 FF        xor di, di             start of framebuffer
0x018   F3 AB        rep stosw              fill 2000 words
                                            ── banner draw ──────────────────
0x01A   BE 4A 7C     mov si, banner         DS:SI → "* kernel-polyglot..."
0x01D   BF B2 07     mov di, 1970           row 12, col 25  (=0x07B2)
0x020   B4 0F        mov ah, 0x0F           white-on-black, hoisted
0x022   AC           lodsb                  load char (loop start)
0x023   84 C0        test al, al            NUL terminator?
0x025   74 03        jz   +3                → animation init
0x027   AB           stosw                  write (char, attr); DI+=2
0x028   EB F8        jmp  -8                next char
                                            ── animation ────────────────────
0x02A   31 ED        xor bp, bp             BP = frame counter
0x02C   45           inc bp                 next frame  ←────┐
0x02D   BF 01 00     mov di, 1              first attr byte   │
0x030   B9 D0 07     mov cx, 2000           cells             │
0x033   89 F8        mov ax, di             AX = byte offset  │
0x035   01 E8        add ax, bp             + frame counter   │
0x037   24 70        and al, 0x70           bg bits only      │ frame loop
0x039   0C 0F        or  al, 0x0F           force white fg    │
0x03B   AA           stosb                  write attr; DI++  │
0x03C   47           inc di                 skip char byte    │
0x03D   E2 F4        loop -12               2000 iter ────────┤
0x03F   B4 86        mov ah, 0x86                              │ INT 15h delay
0x041   31 C9        xor cx, cx                                │  CX:DX = 30000 µs
0x043   BA 30 75     mov dx, 30000                             │  (~33 fps)
0x046   CD 15        int 0x15                                  │
0x048   EB E2        jmp  -30               → .frame ──────────┘
                                            ── data ─────────────────────────
0x04A    30 B        "* kernel-polyglot - Stage 2 *", 0
```

The animation works by walking the 2000 attribute bytes (every odd offset
in the 4000-byte text buffer) and writing
`attr = 0x0F | ((offset + frame_counter) & 0x70)`:

- bits 0–3 of attr → foreground colour, locked to `0x0F` (white)
- bits 4–6 → background colour, cycles `0..7` as offset+frame increments
- bit 7 → blink, masked to zero

Character bytes are never re-written after the initial banner draw, which
is why `make verify-animation` reports `character bytes changed: 0`.

### The build pipeline

```
boot.asm                   ── nasm (in alpine:3 container)
   │                          ─f bin  →  flat 16-bit binary
   ▼
boot.bin   (512 B, ends in 55 AA)
   │                       ── tools/build_polyglot.py:
   │                          • overlays PDF body at offset 0x068
   │                          • computes CRC-32 of readme.txt
readme.txt                   • appends ZIP: LFH + data + CDFH + EOCD
   │                          • writes file, prints byte map to stderr
   ▼
boot.img  (1018 B, MBR + PDF + ZIP)
```

Why a Python builder instead of all-NASM? NASM can't compute CRC-32 at
assembly time, and the ZIP spec requires CRC-32 in both LFH and CDFH
(`unzip -t` enforces it). The Python step is ~120 lines and the *exact
byte layout* is visible in `struct.pack` calls.

Why not deflate? `method=0` (stored, no compression) keeps the data
byte-identical to `readme.txt`. No inflate codec required on the reader
side; CRC-32 is still verified.

## Reproducibility

The build is deterministic — every byte of `boot.img` is reproducible:

- NASM emits the same bytes for the same source.
- The ZIP timestamps are hardcoded (`1980-01-01 00:00`).
- The CRC-32 is a pure function of `readme.txt`.
- The Docker NASM image is cached locally after the first build (look
  for the tag `kernel-polyglot/nasm:local`).

Two consecutive `make clean && make` invocations produce byte-identical
output. Useful sanity check:

```sh
make && cp boot.img /tmp/a; make clean && make && diff boot.img /tmp/a
# (empty output = identical)
```

## Constraints (hard rules from the brief)

- ≤ 1024 bytes total (we hit 1018).
- Bytes `0x1FE..0x1FF` are `55 AA` (BIOS boot signature).
- Every byte must be justified — no zero padding once polyglot work
  begins. The 103 bytes of zero "leftover slack" at `0x197..0x1FD` is
  the only un-claimed region; documented here for transparency, and
  could be reclaimed in a follow-up by extending the PDF body or
  shifting the ZIP backwards. (At this point doing so saves nothing
  visible.)
- All polyglot formats must validate with **real parsers**, not
  "tolerated by accident." Tested under pdfinfo, qpdf, PDFKit,
  python-zipfile, zipinfo, Info-ZIP unzip.
- Visual output must be intentional and recognisable — colour-wave
  animation behind a centred banner.

## Troubleshooting

**`make doctor` reports "MISSING — start Docker Desktop"**
Docker daemon isn't running. Launch Docker Desktop; wait for the whale
icon in the menu bar to settle.

**`make run` opens a blank black window**
The animation may take a second to start after SeaBIOS hands off. If it
stays blank for >5 s, try `make capture-vga` headlessly — if that shows
the banner, the boot is working and the window is a display issue
(check your QEMU build).

**`verify-pdf` errors during `apk add poppler-utils`**
Alpine package mirrors occasionally hiccup. Re-run; or pre-pull with
`docker pull alpine:3`. The PDF body itself is also independently
inspectable via `xxd -s 0x68 -l 304 boot.img`.

**`unzip -tv` says "CRC error"**
Means the build was incomplete or someone edited `boot.img` by hand.
`make clean && make` rebuilds from `boot.asm` + `readme.txt`.
